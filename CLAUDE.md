# Fenly: notes for Claude Code

## Fenly 2.0
- Source of truth: `docs/strategy/ceo-operating-plan.md`. Read it before planning or building any 2.0 work.
- Branches: `fenly-2.0` is the 2.0 trunk. Build each step on its own branch off `fenly-2.0` and merge it back into `fenly-2.0` when tests pass. Never commit to `main`. Tag `v1.0` is the frozen 1.0 prototype; don't move or change it.
- Product rules: hide features behind feature flags instead of deleting them. Keep the brand colors and existing components. The core loop is Fill a room → share link → Find/Apply → filled; every 2.0 change should serve it.
- Version: `package.json` `"version"` (2.0.0) is the only place to set it. `vite.config.ts` passes it to the browser as `__APP_VERSION__`.
- Supabase: the schema lives in `supabase/migrations/` and is run by hand in the dashboard SQL editor (setup steps: `docs/setup/supabase.md`). Put each change in a new numbered file; never edit one that has been run. Every table has RLS. The service-role client (`server/supabase.ts` `getAdminClient`) is used only in `server/`. The browser gets the URL and publishable key from `GET /api/config`, so there are no `VITE_` Supabase vars.
- Feature flags: the list and rules are in `src/config/featureFlags.ts`; turn flags on with `FENLY_FLAGS=scout,ask_fenn` in `.env.local`. In the UI use `useFlag()`; on APIs use `requireFlag()` (404 when off). Hidden tabs fall back to Fill or Find, and 1.0 tabs open from the Find menu.
- Auth: `src/auth/AuthProvider.tsx` handles magic link, Google and phone code. Server routes that need a user use `requireUser()` (`server/auth.ts`). Ask to sign in only at Apply, Publish and Message (`needsSignIn` in `src/utils/authGuards.ts`); browsing stays signed out.
- Analytics: `track(name, props, ctx)` in `server/track.ts`. Add new event names to `EVENT_NAMES`, and also to `CLIENT_EVENT_NAMES` plus `src/lib/analytics.ts` if the browser sends them. Never put personal data in props.
- Fill tab (with Supabase): `src/components/fill/` (FillHome, FillFlow, ShareKit, FillStatusView, ApplySheet), pure rules in `src/fill/` (link codes, attribution, status math, share posts, publish rules; all unit tested), routes in `server/fillRoutes.ts` (owner actions use `getUserClient` so RLS applies). Public listing pages are server HTML at `/r/<code>` (`server/publicPage.ts`, Open Graph tags, every value escaped); `vercel.json` rewrites `/r/*` to the API. Media goes browser → Supabase Storage (`src/lib/fillApi.ts` `uploadToStorage`), never through `/api`. Fair housing is enforced on save and publish (`listingFairHousingIssues`). Without Supabase the Fill tab falls back to the 1.0 demo pages.
- Nav: `FenlyNavBar` (Find = `listings`, Fill = `fill`, Inbox = `messages`, Passport = `passport`). The 1.0 `BottomNavBar` and `HeaderNav` stay in the codebase, unused.
- Find & Apply (with Supabase): pure rules in `src/find/` (filters + `toRoomListing` adapter, fit, lifestyle, Passport level, similar rooms, moderation, host texts), UI in `src/components/find/`, routes in `server/findRoutes.ts`, `hostRoutes.ts`, `inboxRoutes.ts`, `passportRoutes.ts`, `adminRoutes.ts` (+ `notify.ts`, `moderation.ts`, `idCheck.ts`). The Find feed reuses the 1.0 feed components through `toRoomListing`; database rooms have ids `db:<uuid>`.
- Fair housing in matching: anything that scores, sorts, filters or summarizes applicants goes through `toFactualApplicant()` (`src/find/factualApplicant.ts`, an allowlist). `factualApplicant.test.ts` fails if a protected-trait term reaches fields, filters, lifestyle questions or the AI summary prompt; never loosen it, remove the field instead. Names, photos, bios and notes are shown, never scored or sent to the AI.
- Moderation flags, never silently drops: flagged messages are delivered with a warning; a high-risk scam listing is hidden from Find (link still works). Staff review at Passport → Review queue (`FENLY_ADMIN_EMAILS`).
- Notifications: `notify()` writes a `notifications` row (in-app + outbox) and emails through Resend when `RESEND_API_KEY` / `FENLY_EMAIL_FROM` are set; never throws. Daily cron `GET /api/cron/daily` (`CRON_SECRET`) sends move-out reminders.
- ID check (`id_check` flag) is a demo (Gemini look at the document, provider `demo`); replace `runIdCheck` with a vendor before relying on it.
- Launch (PWA + polish): `public/manifest.webmanifest`, `public/sw.js` (hand-written; precaches the shell, cache-first `/assets/*`, network-first pages, never caches `/api`, `/r/`, other origins or range requests; cache names carry the app version), `public/offline.html`, icons in `public/icons/` (regenerate with `npm run icons`: FennMascot `app_icon` → SVG → Remotion `FennAppIcon` stills). The SW registers only in production builds (`src/pwa/registerSw.ts`), so test it with `npm run build` + `NODE_ENV=production npx tsx server.ts`. "Add to Home Screen" shows only after publish or apply (`announceInstallMoment()` → `components/InstallPrompt.tsx`, rules in `src/pwa/installPrompt.ts`).
- Performance: screens and modals in `App.tsx` load through `src/utils/lazyComponent.tsx` (`lazyModal` renders nothing until `isOpen`; `lazyScreen` shows a spinner). Don't import a heavy screen eagerly into `App.tsx`; put shared constants in small modules (`components/homeNav.ts`, `data/locationPresets.ts`). The feed mounts `VideoPlayer` only for the current slide ±1.
- Metrics: `GET /api/admin/metrics?days=7|28` (admins only) → `server/metrics.ts` `buildFunnel` (Part 6 funnel, tested) → Passport → Metrics.
- Copy and accessibility: tab one-liners and empty states live in `src/config/launchCopy.ts` (tested: ≤ 90 chars, no emoji, fair-housing clean). Contrast rule: white text goes on `#B85B3F` (hover `#A9513A`), small orange text uses `#A9513A`; brand `#D06C4E` is for icons, large text and decoration only. `src/config/palette.test.ts` checks the ratios and fails on white-on-`#D06C4E` in 2.0 screens. Tap targets ≥ 40 px, icon buttons need `aria-label`.
- Pre-launch checklist (Supabase, Vercel env, domain, email, legal): `docs/setup/pre-launch.md`. `public/privacy.html` and `public/terms.html` are placeholders that need a lawyer.

Fenly (the UI brand reads "Fenn") is a vertical-video room-rental app exported from Google AI Studio and now developed locally on Windows.

## Stack and layout
- Frontend: React 19 + Vite 8 + Tailwind 4 in `src/`. Main screens in `src/App.tsx`, components in `src/components/`, shared logic in `src/utils/trustSafety.ts`. Listings are still mock data held in React state (`src/data/mockRooms.ts`); the Supabase tables exist (2.0 foundation) but listings move into them with the Fill flow.
- API: one Express app in `server/app.ts` holds every `/api/*` route. `server/gemini.ts` has the shared Gemini client and the model IDs.
- Local runner: `server.ts` (`npm run dev`) serves the API and the Vite dev server on http://localhost:3000. Hot reload is off: refresh the browser after frontend edits, and restart the server after editing `server/` or `.env.local`.
- Vercel: `api/index.ts` exposes the same Express app as one function; `vercel.json` pins the Vite preset and rewrites `/api/*` to it. Vercel caps request bodies at 4.5 MB, so media is never posted through `/api`: upload it to storage and send references.

## Commands (Windows; in PowerShell use npm.cmd / npx.cmd)
- `npm run dev`: app + API on port 3000
- `npm run lint`: TypeScript check (`tsc --noEmit`)
- `npm run build`: production build; it fails if the Gemini key would leak into the browser bundle
- `npm test`: every unit test (`src/**/*.test.ts`, `server/*.test.ts`)
- `npx tsx --test src/utils/trustSafety.test.ts`: one test file

## Rules
- Don't change existing pages, brand colors, layout, or features unless the task asks for it. Reuse the existing palette and component styles.
- Secrets live only in `.env.local` (gitignored) and are read on the server: `GEMINI_API_KEY`, `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `SUPABASE_PUBLISHABLE_KEY` (public, but served through `/api/config`), `FENLY_FLAGS`, `RESEND_API_KEY`, `FENLY_EMAIL_FROM`, `FENLY_ADMIN_EMAILS`, `CRON_SECRET`. Never print them, never commit them, never give them a `VITE_` prefix. `VITE_GOOGLE_MAPS_API_KEY` is a public, referrer-restricted browser key.
- Gemini: follow the `gemini-api-dev` skill in `.claude/skills/` and fetch the doc pages it lists before writing Gemini code. Keep model IDs in `server/gemini.ts`. For `gemini-3.8-flash`, the thinking level must be low, medium or high (never `minimal`, never `thinking_budget`), and don't send temperature, top_p, top_k or candidate_count. Use structured JSON output with a schema for anything the UI parses.
- Put every new backend route in `server/app.ts` (or a module it registers) so it works locally and on Vercel.
- Git: commit checkpoints with clear messages and stage with `git add -A -- . ':!.aistudio'`. The AI Studio screenshots in `.aistudio/` show as modified because a C2PA tag was added when they were copied; never commit those changes. Never commit `.env*` files except `.env.example`.

## Viral video editor (Remotion)
- What it does: turns the 5 guided shots (7 s each) into a 1080x1920 short: a 30-45 s full tour (hook, listing facts, up to ~7 s per room with speed ramps and two callouts, slow-motion perk reveal, price question, seamless loop). Rooms shrink to their clean footage, so short or messy clips give shorter tours.
- Create Listing makes the choices: price hook (headline text editable), full tour, balanced pace, automatic lighting (`look.ts` `autoLook`), no sound effects or room sound. Music is switched off for now (`MUSIC_ENABLED = false` in `ViralVideoEditor.tsx`); the AI music code (`POST /api/viral/music`, `musicMood.ts`, `aiMusic.ts`: a song the host likes -> mood -> original Lyria instrumental) stays in place for later. The edit screen (`EditListingModal`, from Home > Landlord > Active Room Listing: swipe left on phones, Edit button on computers) re-opens a listing's saved edit (`RoomListing.viralEdit`: clips, analysis, AI copy, settings) with hook style, length, pace, lighting presets and sliders, sound, music and a typed AI box. Typed requests are understood locally first (`editSettings.ts` `localEditPatch`); the rest go to `POST /api/viral/edit` (text only, flash-lite, minimal thinking). Section timing, speeds and sources: `docs/viral-playbook.md`. Build brief: `docs/briefs/viral-remotion-editor.md`.
- Dev server: `npm run dev` runs `tsx watch`, so it restarts when server code changes; live reload shares port 3000 (`DISABLE_HMR=true` turns it off). The editor is lazy-loaded, so every `remotion` / `@remotion/*` import path must be listed in `optimizeDeps.include` in `vite.config.ts`, or the first open re-bundles React mid-session and the page goes blank.
- Code: `src/remotion/viral/`. `plan.ts` builds a JSON edit plan (pure, unit tested); `FenlyViralTour.tsx` renders it. `src/components/ViralVideoEditor.tsx` shows it in `@remotion/player` and exports MP4 in the browser with `@remotion/web-renderer` (no render server, works on Vercel). Studio entry: `src/remotion/index.ts`.
- Load the `remotion-*` skills in `.claude/skills/` before editing Remotion code. Keep every `remotion` / `@remotion/*` package on the same exact version.
- Editing quality: before changing or judging how the video looks or feels (hook, length, speed, cuts, fonts, text size and placement, reading time, color, sound), load the `fenly-viral-editor` skill. It brings in `short-form-video` and `caption-animation` (installed from iart-ai/tiktok-video-skills, pinned in `skills-lock.json`), and its `references/audit.md` scores a render frame by frame. Audit a real render before and after every change.
- Composition code uses inline styles (no Tailwind), brand tokens from `src/remotion/viral/theme.ts`, and keeps all text inside `SAFE` so platform UI never covers it. No emoji in burned-in text. No CSS `filter` in the composition (unsupported by client-side rendering in Safari); use `@remotion/effects`.
- Photo tour (`photo_tour` flag, off by default; a demo feature): Find's demo rooms play their stills as a moving tour (`photoTour.ts` builds the plan, `utils/photoTourListing.ts` maps a listing, `components/PhotoTourPlayer.tsx` plays it, lazy-loaded by `VideoPlayer`). Its text runs at `PHOTO_TEXT_SCALE` (0.64) through `plan.textScale`. Each photo shot pans one way only (up, down, left or right, `PAN_DIRECTIONS` taking turns; no bob or zoom). Demo photo labels must describe what the photo shows; the last label becomes "The best part".
- Tests: `npx tsx --test src/remotion/viral/*.test.ts`. Change timing rules in `plan.ts` only together with its tests.
- Never commit the host's clips (`public/samples/`) or renders (`out/`).
